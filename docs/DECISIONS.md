## 2026-09-25: Batch 1 spec

| #   | Topic               | Decision                                                                                                                                                                                                                                                                                                                |
| --- | ------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 8   | Roles               | **One role per user** in `profiles.role` (buyer, vendor, admin). Replaces the earlier multi-role table. Every signed-in account can use buyer features; the role only adds access. Nobody changes their own role (admins included); only admins change other people's roles. Enforced by a trigger.                     |
| 9   | Fee rules           | `fee_rules.value` is split: `amount_minor bigint` for `flat` and `per_kg`, `percent numeric(7,4)` for `percent` (5.5 = 5.5%). A check constraint requires exactly the right one.                                                                                                                                        |
| 10  | Buyer order writes  | Buyers create orders only as `draft` or `quote_requested` and edit only drafts. They never change status after that, nor `vendor_id`, `delivery_code_hash`, `link_preview_json` or `public_tracking_token`. Later status changes go through server code. Buyers cannot write order items; prices come from server code. |
| 11  | Vendor order writes | Vendors read their assigned orders only. Actions (accept, purchased, inspection upload) arrive in Batch 6 as server functions that check the current status. Vendors cannot change their own `status`, `owner_id` or `verification_notes`.                                                                              |
| 12  | Vendor approval     | `approve_vendor()` sets the vendor to approved and the owner's role to vendor in one transaction; `suspend_vendor()` reverses it. Both admin-only and logged.                                                                                                                                                           |
| 13  | Public vendor data  | The public reads `vendor_directory` (id, business name, country of approved vendors). The `vendors` table, which holds payout details, is owner and admin only.                                                                                                                                                         |
| 14  | Ledger              | Append-only for everyone, service role included. Amounts are always positive; `entry_type` gives the direction. Corrections are new `adjustment` rows.                                                                                                                                                                  |
| 15  | Server-only tables  | Clients cannot insert into `ledger_entries`, `audit_log`, `payments` or `notifications` (no grants). Only server code with the service role key writes them.                                                                                                                                                            |
| 16  | Reference data      | Currencies, countries, corridors and placeholder fee rules live in `supabase/seed.sql` (idempotent). Hosted projects need `db push --include-seed` once.                                                                                                                                                                |
| 17  | Countries           | Kept a `countries` table (not in the original list) for country code integrity and the sign-up picker.                                                                                                                                                                                                                  |

Other choices:

- Role and vendor status are read from the database on each request, not stored in the JWT. A change takes effect on the next page load.
- Blocked users are sent to `/unauthorized`; logged-out users to `/login?next=...`.
- Phone numbers are stored in E.164 format (`+2348031234567`).
- Email confirmation is on. Passwords need 8+ characters with a letter and a number.

## 2026-09-30: Hardening before Batch 2

| #   | Topic                 | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| --- | --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 18  | Payout details        | Vendors never write live `payout_details_json` after applying. They call `request_payout_change()`, which stores a pending copy and returns a random token. An admin approves with `approve_payout_change(vendor_id, token)` or discards with `reject_payout_change()`. A newer request invalidates the token, so nothing is approved unseen. Payouts must read `payout_details_json` only, never the pending column. The audit log records that a change happened, never the account numbers. Browser sessions cannot edit these columns at all, admins included. |
| 19  | Product image storage | Bucket `product-images`: public read (fast CDN loads), 5 MB limit, JPG/PNG/WebP only. Path: `<vendor_id>/<product_id>/<random>.<ext>`. Only the owning approved vendor (or an admin) can upload, list or delete, and only inside their own vendor folder. Trade-off: anyone with the exact URL can fetch a file, even for an unpublished product. URLs hold two random UUIDs, so they cannot be guessed. Switch to a private bucket with signed URLs if that is not acceptable.                                                                                    |
| 20  | Image rows            | A `product_images` row must point at a file inside its own product folder (no other vendor's files, no `..`, no other extensions), and a product has at most 10 images.                                                                                                                                                                                                                                                                                                                                                                                            |
| 21  | Migration hygiene     | Changes after Batch 1 are new migration files, never edits to applied ones.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

## 2026-10-01: Batch 2, vendors and catalog

| #   | Topic                 | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| --- | --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 22  | Price filter and sort | Products are listed in their vendor's currency and converting needs the FX engine (Batch 4). So the price range filter and both price sorts work on the listed amount within one chosen currency, and are ignored (with a hint) until a currency is chosen. Batch 4 replaces this with a converted sort.                                                                                                                                                                                                                                     |
| 23  | Prohibited terms      | Enforced by a database trigger (table `prohibited_terms`), not only in app code, because an approved vendor can call Supabase directly. `lib/catalog/prohibited.ts` holds the same list for instant feedback in the form, and a database test compares the two lists and their matching. A match saves the product inactive and flagged. It stays flagged until an admin clears it, so rewording cannot be retried until it passes. Scanned: title, description, brand, condition notes and spec values. Whole words only, case-insensitive. |
| 24  | Flagged product queue | `/admin/products` lists flagged products with "Clear flag" (`clear_product_flag`, logged). Leaving a flag in place keeps the listing hidden. Clearing does not publish: the vendor publishes it.                                                                                                                                                                                                                                                                                                                                             |
| 25  | Private vendor data   | No split table for payout details. The `vendors` table is readable only by its owner and admins (phone, registration number, ID document path and payouts included). Visitors read the `vendor_directory` view: id, business name, country, city, categories and created date of approved vendors. A test proves visitors, buyers and other vendors cannot read the private columns.                                                                                                                                                         |
| 26  | Vendor status         | New status `rejected`. Transitions: pending to approved or rejected; approved to suspended; suspended to approved (reinstate); rejected to pending, which only the owner can do by resubmitting the same record (still one record per user; the reason is cleared). Reject and suspend need a reason of at least 5 characters, which the vendor sees. After approval the owner cannot change business name, country, city, registration number or ID document. Phone and categories stay editable.                                           |
| 27  | Product images        | At most 6 per product (database trigger). Bucket limit 1 MB, because the browser compresses to about 300 KB first (longest side 1600px, WebP). The 5 MB limit applies to the original file, in the browser. Browsers that cannot encode WebP (older Safari) get JPEG at the same size target. Upload path `<vendor_id>/<product_id>/<file>` where the product must belong to the vendor. Admins may view and delete photos but not upload.                                                                                                   |
| 28  | ID documents          | Private bucket `vendor-documents`, path `<user_id>/<file>`. The owner uploads and reads their own file. Admins open it through `/admin/vendors/<id>/document`, which makes a fresh 60-second signed link and writes an audit row before redirecting. Logged-out visitors get nothing: the bucket has no public URL and no visitor policy.                                                                                                                                                                                                    |
| 29  | Demo data             | `supabase/seed-dev.sql` is separate from `seed.sql` and refuses to run unless `mapk.dev_seed` is set to `yes`. Demo users have no password and no login record. Demo pictures use `demo/<name>.webp` paths served from `/public/demo`; only server-side code can write such rows.                                                                                                                                                                                                                                                            |
| 30  | Listing rules         | A product's route must be active and start in the vendor's country. A product needs at least one image to be published. Price must be above zero and under 10,000,000,000 in normal units. Stock of zero stays listed as "Out of stock". Products that were ordered cannot be deleted; they are hidden instead. The public shop always reads as a visitor (`createPublicClient`), so an admin browsing it sees what visitors see.                                                                                                            |

## 2026-10-08: Batch 3, link orders and admin quoting

| #   | Topic                   | Decision                                                                                                                                                                                                                                                                                                                                                 |
| --- | ----------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 31  | Order state machine     | The allowed moves live in the table `order_status_transitions` (42 pairs). A trigger refuses any status change that does not come through `transition_order()`, which only the service role can call. `lib/orders/state-machine.ts` holds the same map for fast errors, and a test compares the two and checks all 324 pairs.                            |
| 32  | Creating orders         | Direct INSERT and UPDATE on `orders` are revoked from signed-in users. Link orders are created only by `create_link_order()`, which checks the link, store, recipient and currency, and enforces 10 link requests per buyer per 24 hours (cancelled ones count). Vendors cannot read link orders.                                                        |
| 33  | Stores                  | Table `store_domains` (admin edits it). A host matches a store if it equals the domain or is a subdomain, longest match wins. Unsupported stores (Amazon) are refused with a clear message. Unknown stores are accepted for manual quoting, with no route until the admin picks one. Buyers read the `store_directory` view, never the table.            |
| 34  | Link previews           | Only `og:title`, `og:description` and `og:image` are read, and only for stores with `preview_allowed`. The form shows a preview on leaving the field (display only). The order fetches and saves its own preview after it is created, with the service role. A missing preview never blocks an order. Pictures are shown from the store, not copied.     |
| 35  | SSRF protection         | https only, port 443 only, no user name in the link, no IP-address hosts. The host is resolved by us and every address must be public. The connection is pinned to the checked address (undici), redirects (max 3) are checked the same way, with a 5 second limit and 1 MB cap, HTML only. Tests cover private ranges, metadata address and DNS tricks. |
| 36  | Quotes                  | A quote has 1 to 20 lines, one of them an item price above zero. The total is computed in the database from the lines; no total is accepted from the browser. Expiry is 24, 48 or 72 hours (default 48). Sending a revision supersedes the old quote. Sent quotes can never be edited, by anyone. The buyer sees only the latest quote.                  |
| 37  | Internal notes          | Admin notes live in a separate table `quote_internal_notes` that only admins can read, so no query by a buyer can return them.                                                                                                                                                                                                                           |
| 38  | Over budget             | If the total is above the buyer's budget, the admin must tick a confirmation. This is checked in the app and again in `send_quote()`.                                                                                                                                                                                                                    |
| 39  | Expiry                  | Expiry is enforced three ways: `expire_due_quotes()` runs every 15 minutes (pg_cron), a quote is checked when the buyer opens the order, and `accept_quote()` checks again. Accepting a quote that ran out returns "expired" and saves the new statuses, so a late job can never let an expired quote through.                                           |
| 40  | Declines                | Admin can decline only a request that has no quote yet, with one of five reasons (a note is required for "other"). Buyer declining a quote cancels the order. An expired quote can be re-requested by the buyer, which puts the order back in the admin queue.                                                                                           |
| 41  | Messages                | Buyer and admin messages on an order. Sender and admin flag are set by the database, messages cannot be edited or deleted, buyers can send 20 per hour per order, and read markers are kept for unread badges.                                                                                                                                           |
| 42  | Recipients              | Nigerian mobile numbers only (`+234` and 070x, 080x, 081x, 090x, 091x) because the delivery code goes by SMS. The state must be one of the 36 states or FCT (table `regions`). Once an order uses a recipient, state, city, address and country are locked; name, phone and landmark can still change. A used recipient is archived instead of deleted.  |
| 43  | Notifications outbox    | Notification status `queued` is now `pending`. `audience = 'admins'` targets all admins. Emails are only queued in this batch; sending is Batch 7.                                                                                                                                                                                                       |
| 44  | Service role at runtime | The app server now needs `SUPABASE_SERVICE_ROLE_KEY` (server only, never `NEXT_PUBLIC_`). It is used for two things: saving link previews and moving an order between statuses through `transitionOrder`. The caller is always checked first.                                                                                                            |
